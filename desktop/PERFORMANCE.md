# Still Browser 最適化の記録（2026-10-13）

現行Windows版のRust/Tauri実装とLinuxのセッション移行処理に変更を適用した。既存の操作、配色、保存JSON形式、エンジンのキャッシュ・セキュリティ設定を維持している。新しい依存ライブラリは追加していない。

**調査範囲と責務**

| 系統 | 構成 | 確認した責務 |
|---|---|---|
| Windows現行版 | Rust / Tauri 2 / WebView2、TypeScript / HTML / CSS | `core` が状態遷移、`src-tauri` がウィンドウ・IPC・COM・I/O、`ui` が表示を担当 |
| Linux版 | Pythonランチャー / Firefox ESR 140.17.0 / Gecko、userChrome CSS | ランチャーと一度限りの移行処理がアプリ側。タブ、通信、描画、サイトの保存はFirefox側 |
| Windows旧版 | C# / .NET 8 / WPF / WebView2 | 比較用として残されている実装。同期保存、全タブの選択スタイル更新を確認したが今回の変更対象に含めていない |

現行版はメインスレッドでネイティブUI/COMを扱い、非同期コマンドとイベントがSessionのMutexを共有する。別スレッドが16ms間隔でイベントをまとめ、別の保存スレッドが800ms間隔で保存する。復元されたページは選択までWebViewを作成しない。履歴は500件、UIの履歴一覧は30件、完了ダウンロード履歴は200件を基準としている。

**問題、根拠、適用した修正**

| 影響 | 原因・確認方法 | 修正 |
|---|---|---|
| データ消失 | バックアップ失敗をログだけで処理し、既存バックアップがあれば新しい元データの保護を省略していた | バックアップ成功まで上書きを禁止。失敗は再試行し、衝突時は別名を作る。失敗再現テストで元データの維持を確認 |
| 保存競合・応答性 | 定期保存と終了時保存が同じ一時ファイルを使用し、状態のJSON化もSessionロック内だった | 保存全体を専用Mutexで直列化。終了時は実行中保存を待つ。所有データだけをロック内で取得し、JSON化とI/Oを外へ移動。書き込みをsyncしてから原子的に置換 |
| WebView保持・復旧の競合 | 作成完了前にタブが閉じられても無条件にWebViewを保持し、旧プロセスのイベントも同じタブIDに適用していた | 作成世代を検証。古い作成結果はcloseし、古いタイトル・履歴・クラッシュ・全画面イベントを無視。復旧時の所有権の除去も状態変更と同じロック範囲で行う |
| 大量タブ時のCPU・割り当て | ID検索の線形走査、1タイトルの変更で全タブの文字列を複製・送信。変更前後の同一マイクロベンチマークで確認 | ID→位置の索引を追加。構造変更時だけ全一覧、通常は変更IDの集合を送り、同じタブのイベントをまとめる |
| 不要なDOM更新 | 毎回のJSON.stringifyと一覧全置換。変更前のUIテストも全置換を前提としていた | IDごとに行を再利用し、変更行と新旧の選択だけ更新。MutationObserverで1文字ノードの更新、行・フォーカス保持を確認 |
| 再描画とIPC | 1種類のライブラリ変更で全一覧を再送し、同じテーマ属性などを書き続けた | ブックマーク・履歴・ダウンロードの無効化を分離。変わっていない属性と設定ペインの再描画を省略 |
| 起動時の表示整合性 | イベント登録が完了する前に初期状態を要求できた | 登録を待ってからready。単調増加revisionで古い配信を除外。初期化失敗時は購読・待機データを解放 |
| 長時間のメモリ保持 | 同時ダウンロードが200件を超えると、終了しても次回開始まで履歴が上限へ戻らなかった | 完了時にも整理。進行中は残し、250件の開始・完了テストで200件へ戻ることを確認 |
| Linux移行のコピー量 | LZ4の4バイト一致でもoffsetまでの最大65,535バイトを毎回コピー | 一致に必要な範囲だけをコピー。重なりのある一致・サイズ上限・切れた入力もテスト |
| プライバシー | ダウンロード元URL全体をログに書いていた | ホスト名だけを記録し、クエリやURL内の認証情報をログへ追加しない |

**性能計測**

Ubuntu 24.04.5 x86_64、Linux 6.8.0-146-generic、Rust 1.96.0。release設定は既存の`opt-level=s`、LTO、1 codegen unit。変更前Sessionの隔離コピーと変更後で同じ`core/examples/performance.rs`を実行した。各ケース2,000反復、前後の実行順を交互にした5回の中央値を示す。ほかのビルド・UIテストの完了後に比較した。

時刻計測にはSessionの操作とSnapshot生成・破棄を含む。JSONシリアライズ、Tauri IPCの配送、WebView生成・ページ描画、ネットワーク、ディスクは含まない。したがって、これは実ブラウザのタブ切り替え完了時間・ページ表示速度ではない。URLは合成データで実際にはアクセスせず、ブラウザのHTTPキャッシュは測定対象外。初回Snapshotを取得した後のメモリ内状態を繰り返し処理した。

| タブ数 | 切り替え＋状態生成 µs（前 → 後） | タイトル更新＋状態生成 µs（前 → 後） | 更新JSON bytes（前 → 後） |
|---|---:|---:|---:|
| 10 | 0.650 → 0.192 | 0.698 → 0.324 | 1,329 → 513 |
| 1,000 | 92.973 → 0.206 | 93.268 → 0.327 | 97,181 → 513 |
| 10,000 | 1105.541 → 0.254 | 1064.253 → 0.323 | 988,188 → 525 |

JSON量は別途1件のタイトル変更をシリアライズしたサイズ。全タブの文字列複製を変更タブだけに限定したため、更新時の一時的な割り当ても減る。ただし索引用Mapと保存中の所有Snapshotのメモリは追加される。実ブラウザ全体のRSS削減率は測定していない。

Linux移行は、offset=65,535の4バイト一致を10,000回含む95,823バイトの合成LZ4入力で、9回の中央値が54.431ms → 13.708msだった。結果の文字列は105,541文字で一致した。これは当該パターンのデコード測定であり、通常起動全体の改善率ではない。

UIはFirefox ESR 140.17.0のheadless、モックバックエンド、ローカルHTTP配信で検証。ライト・ダーク両方で、同一フレーム内の50タイトル変更が文字ノード1個の更新にまとまり、一覧の置換は0回。追加1,000タブの背景タイトル更新も文字ノード1個・テーマ属性変更0回で、行とフォーカスを維持した。背景タブ削除時は対応する行が一覧から消えることを確認した。プロセスのリークがないことまでを示すテストではない。

生データは[core-results.json](../artifacts/performance/core-results.json)、変更前比較用ソースは[baseline-core.tar.gz](../artifacts/performance/baseline-core.tar.gz)。比較用コピーは変更前のSessionを保持し、今回の保存保護コードは測定経路で実行していない。

**実機での未確認事項と残る制約**

Windowsの起動時間、5/20タブのRSS、長時間稼働時のCPU/GPU、ページ読み込み時間、COM/レンダラーの実クラッシュ復旧、保存中のプロセス強制終了・電源断、ダウンロード失敗時の不完全ファイルの扱いは未検証。Windows配布EXE・インストーラー（x64 / ARM64）は変更後のコードで再ビルドしたが、Windows実機での起動は未確認。

WebView2/Firefox内部のレンダリング、JS実行、HTTPキャッシュや通信を高速化したとは主張しない。TLS/Same-Origin Policy/サンドボックス、特権APIの呼び出し元チェックは弱めていない。音声再生の除外と既存の遅延復元を維持した。休止処理の適用範囲は増やしていない。TrySuspendの拒否条件や可視化時の自動復帰は[Microsoftの仕様](https://learn.microsoft.com/en-us/microsoft-edge/webview2/reference/win32/icorewebview2_3?view=webview2-1.0.3650.58#trysuspend)を確認したが、フォーム・メディア・ダウンロードとの実機互換性は追加確認が必要。

一覧の初回表示・追加削除は依然O(N)で、DOMの仮想化は導入していない。大量の実ページを保持した際のエンジン側メモリ、数万ブックマーク、サイズの大きいstate.jsonの起動時読み込みは、実機プロファイルを得てから次の改善対象を決める。保存時のsyncは耐障害性を優先するため、遅いディスクでの終了待ち時間には影響し得る。単一の保存プロセス内は直列化したが、旧WPF版と同時に起動して同じ保存先を共有する運用は未対応。

## メモリ最適化（2026-10-13 第2回）

**調査で分かったこと**

| 区分 | 担当 | 状況 |
|---|---|---|
| ページの描画・JS・キャッシュ | WebView2（別プロセス群） | RAMの大部分を占める。一度表示した背景タブは、閉じるまでWebViewが残っていた。保持中はメモリ目標を「低」にし、`TrySuspend`で凍結するだけだった。OSのメモリ不足通知には反応していなかった |
| UI | WebView2（`UI`フォルダの別環境） | ページ用とは別のブラウザプロセス群になる。ページエンジンがクラッシュしてもUIが残るようにする設計（R6）のため、今回は変更していない |
| 状態管理・保存・IPC | Rust（`core`・`src-tauri`） | ヒープは数百KB規模。リーク・循環参照はない（Arc/Mutexの保持はAppHandleと短命タスクのみ、チャネルは容量1）。ただし、無駄な確保と再送を確認した（下表） |

**変更内容**

| 対象 | 原因 | 修正 |
|---|---|---|
| 背景タブ（エンジン側、Windows） | メモリ不足でもページを解放する手段がなかった | 非表示にする時点で、ページに失う内容がないかをスクリプトで確認してから凍結する。凍結中のページは変化しないため、この結果は再表示まで有効。Windowsの低メモリ通知（`CreateMemoryResourceNotification`）をカーネル内で待ち、通知が出ている間は5秒ごとに1つずつ、最後に表示してから最も時間が経ったタブのWebViewを閉じる。タブは一覧に残り、選択すると再読み込みされる |
| 解放の対象外 | 状態が分からないときは保護する | 表示中・アクティブ・全画面のタブ、音声を再生中のタブ、自分が開始したダウンロードが進行中のタブ。編集済みの入力欄・選択・チェック・添付ファイル、`contenteditable`・`designMode`、`onbeforeunload`、中身を調べられないクロスオリジンのframeがあるタブ。確認スクリプトが失敗したタブ |
| ページ読み込みごとのIPC（Rust→UI） | 読み込みのたびに、ブックマーク一覧全体を作り直して送っていた（ブックマークの題名は履歴から決まるため） | 題名が変わり得るときだけ送る。対象は、ブックマーク済みのページへの訪問と、上限で消える最古の履歴がそのブックマークの最後の題名だった場合 |
| 設定のIPC | 毎回の更新に設定一式を複製・送信していた | 変更時と初回の完全版のときだけ送る |
| 起動時の読み込み | `state.json`全体を一度`serde_json::Value`の木に展開していた | 型付き構造体に直接読み込む。null・オブジェクト以外の要素・型の誤りの扱いは従来と同じで、テストで固定した |
| 保存 | 状態全体のJSON文字列を作ってから書き込んでいた | 32KBのバッファで一時ファイルへ直接書き込む。Windowsで開いたままのファイルは改名・削除できないため、失敗時も必ず閉じてから削除する |
| タブ表 | 大量のタブを閉じても、Vec・HashMap・HashSetがピーク時の容量を保持していた | 4分の3が空いたら半分に縮める（償却O(1)） |

**計測（Rust側ヒープ）**

`core/examples/memory.rs`で計測した。Ubuntu 24.04.5 x86_64、Rust 1.96.0、release（`opt-level=s`・LTO・codegen-units=1）。グローバルアロケータを数える方式で、確保・解放のバイト数と回数を正確に数えるため、3回とも同じ値になった。変更前は[baseline-core-memory.tar.gz](../artifacts/performance/baseline-core-memory.tar.gz)のコピーに同じシナリオを実行した。保存のシナリオだけは、それぞれのシェルが実際に行う手順に合わせている（変更前は文字列を作ってから書き込み、変更後は直接書き込み）。生データは`artifacts/performance/memory-{before,after}.csv`。

プロファイル：タブ100、ブックマーク1,000、履歴500、ダウンロード200（`state.json`は約160KB）。

| シナリオ | 指標 | 変更前 | 変更後 | 差 |
|---|---|---:|---:|---:|
| ページ読み込み1回（履歴の1割がブックマーク済み） | UIへの送信量 | 78,709 B | 10,586 B | −86.5% |
| 同上 | 確保回数 | 1,146 | 200 | −82.5% |
| 同上（200回） | 最大一時ヒープ | 273,723 B | 237,723 B | −13.2% |
| 同上（200回） | 終了後に増えた保持量 | +31,854 B | −4,146 B | 履歴リストの再確保がなくなった |
| 起動時の読み込み | 最大一時ヒープ | 890,494 B | 423,794 B | −52.4% |
| 同上 | 確保回数 | 7,574 | 3,361 | −55.6% |
| 同上 | 読み込み後の保持量 | 211,718 B | 221,862 B | +4.8%（下記） |
| 保存1回 | 最大一時ヒープ | 457,314 B | 231,098 B | −49.5% |
| 5,000タブの開閉×10 | 終了後に残る量 | 856,960 B | 16,768 B | −98.0% |
| 20,000回の読み込み（50回ごとに保存） | 確保回数の合計 | 23,390,951 | 3,454,436 | −85.2% |

起動後の保持量が増えたのは、要素数を知らずに読み込むリストの予備容量と、タブ・ダウンロードに追加した管理項目（約5KB）のため。履歴は常に上限の500件近くあり、変更前は最初のページ読み込みで履歴リストが倍の容量へ再確保され、約32KB増えていた。変更後は予備容量に収まるため、この再確保は起きない。読み込み直後に容量を詰める処理も試したが、次の追加で再確保が起きて合計が増えたため採用していない。

履歴がすべてブックマーク済みのページという最悪の条件では、送信量は94,168 B → 93,986 Bで、ほとんど変わらない。最古の履歴が消えるたびに、ブックマーク行の題名が実際に変わるためで、送信が必要な更新だけが残っている。

**計測していないもの**

WebView2はこの環境（Linux）では動かない。そのため、起動直後・1/5/20タブ・休止後・全タブを閉じた後・長時間稼働時の、プロセスツリー全体のPrivate Bytes／Working Setは計測していない。背景タブの解放によるRAM削減量や、低メモリ通知が実際に届くかも未確認。上の数値はRust側ヒープだけで、ブラウザ全体のRAM削減率ではない。Windows用のコードは`cargo xwin clippy`（x64・ARM64）で型検査のみ行った。`artifacts`のWindows用EXE・インストーラーは、この変更より前のビルドのまま。
